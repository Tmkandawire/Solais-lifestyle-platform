# 1. Purpose

This document defines the step-by-step implementation of the PostgreSQL
and Prisma foundation for the Solaís Lifestyle Platform.

By the end of this phase, the backend will have:

-   A PostgreSQL development database
-   Prisma initialized and configured
-   A reusable Prisma client
-   Core identity and authorization models
-   Role-specific profile models
-   Session persistence
-   Initial enums, constraints and indexes
-   A first migration
-   Seeded platform roles and a development administrator
-   Database-aware health and readiness checks
-   Database lifecycle and shutdown handling
-   Database verification tests

This phase establishes the database foundation only. Event, ticketing,
payment, gallery, journal and application workflow models will be added
in their approved feature phases.

# 5. Create the Local PostgreSQL Database

Open PostgreSQL:

``` bash
psql -U postgres
```

Create the development database:

``` sql
CREATE DATABASE solais_development;
```

Create a dedicated application user:

``` sql
CREATE USER solais_app WITH ENCRYPTED PASSWORD 'replace-with-a-strong-local-password';
```

Grant access:

``` sql
GRANT ALL PRIVILEGES ON DATABASE solais_development TO solais_app;
```

Connect to the database:

``` sql
\c solais_development
```

Grant schema permissions:

``` sql
GRANT ALL ON SCHEMA public TO solais_app;
ALTER SCHEMA public OWNER TO solais_app;
```

Exit:

``` sql
\q
```

For managed PostgreSQL, use the connection string supplied by the
provider and do not create users manually unless required.

# 9. Database Naming Conventions

Use:

  Item                 Convention                 Example
  -------------------- -------------------------- ----------------------
  Prisma models        PascalCase, singular       `UserProfile`
  PostgreSQL tables    snake_case, plural         `user_profiles`
  Prisma fields        camelCase                  `createdAt`
  PostgreSQL columns   snake_case                 `created_at`
  Primary keys         UUID                       `id`
  Foreign keys         relation name + `Id`       `userId`
  Timestamps           `createdAt`, `updatedAt`   mapped to snake_case
  Enums                PascalCase                 `AccountStatus`
  Enum values          UPPER_SNAKE_CASE           `EMAIL_VERIFICATION`

Use `@map` and `@@map` so application naming remains idiomatic
TypeScript while PostgreSQL naming remains idiomatic SQL.

# 12. Define the Role Model

``` prisma
model Role {
  id          String   @id @default(uuid()) @db.Uuid
  code        RoleCode @unique
  name        String   @unique @db.VarChar(100)
  description String?  @db.VarChar(255)
  isSystem    Boolean  @default(true) @map("is_system")
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  users User[]

  @@map("roles")
}
```

Purpose:

-   Stores platform roles
-   Separates role identity from user records
-   Supports stable RBAC checks through `RoleCode`
-   Allows human-readable names and descriptions

# 13. Define the User Model

``` prisma
model User {
  id              String        @id @default(uuid()) @db.Uuid
  roleId          String        @map("role_id") @db.Uuid
  firstName       String        @map("first_name") @db.VarChar(100)
  lastName        String        @map("last_name") @db.VarChar(100)
  email           String        @unique @db.VarChar(255)
  phone           String?       @db.VarChar(30)
  passwordHash    String        @map("password_hash") @db.VarChar(255)
  avatarUrl       String?       @map("avatar_url") @db.Text
  status          AccountStatus @default(PENDING_VERIFICATION)
  emailVerifiedAt DateTime?     @map("email_verified_at")
  lastLoginAt     DateTime?     @map("last_login_at")
  createdAt       DateTime      @default(now()) @map("created_at")
  updatedAt       DateTime      @updatedAt @map("updated_at")

  role             Role              @relation(fields: [roleId], references: [id], onDelete: Restrict, onUpdate: Cascade)
  attendeeProfile  AttendeeProfile?
  vendorProfile    VendorProfile?
  partnerProfile   PartnerProfile?
  sessions         Session[]

  @@index([roleId])
  @@index([status])
  @@index([createdAt])
  @@map("users")
}
```

Rules:

-   Normalize email to lowercase before persistence
-   Never store plaintext passwords
-   Do not expose `passwordHash` through API responses
-   A user has one primary platform role in the MVP
-   Role-specific information belongs in profile tables
-   Account deletion is not implemented as a hard delete during the MVP

# 17. Define the Session Model

``` prisma
model Session {
  id               String    @id @default(uuid()) @db.Uuid
  userId           String    @map("user_id") @db.Uuid
  tokenHash        String    @unique @map("token_hash") @db.VarChar(255)
  userAgent        String?   @map("user_agent") @db.Text
  ipAddress        String?   @map("ip_address") @db.VarChar(64)
  expiresAt        DateTime  @map("expires_at")
  lastUsedAt       DateTime? @map("last_used_at")
  revokedAt        DateTime? @map("revoked_at")
  createdAt        DateTime  @default(now()) @map("created_at")
  updatedAt        DateTime  @updatedAt @map("updated_at")

  user User @relation(fields: [userId], references: [id], onDelete: Cascade, onUpdate: Cascade)

  @@index([userId])
  @@index([expiresAt])
  @@index([revokedAt])
  @@map("sessions")
}
```

Security rules:

-   Store only a cryptographic hash of the refresh token
-   Never store raw refresh tokens
-   Revoke sessions during logout, password changes and security events
-   Delete or archive expired sessions through scheduled maintenance
    later

``` typescript
const globalForPrisma = globalThis as unknown as {

  globalForPrisma.prisma ??
```

# 23. Connect the Database During Startup

Update:

``` text
src/server.ts
```

Use an asynchronous bootstrap:

``` typescript
import { app } from './app.js';
import { connectDatabase, disconnectDatabase } from './config/database.js';
import { env } from './config/env.js';
import { logger } from './shared/logger/logger.js';

async function bootstrap(): Promise<void> {
  await connectDatabase();

  const server = app.listen(env.PORT, () => {
    logger.info('Solaís API started', {
      environment: env.NODE_ENV,
      port: env.PORT,
    });
  });

  async function shutdown(signal: string): Promise<void> {
    logger.info(`${signal} received. Shutting down gracefully.`);

    server.close(async (error) => {
      if (error) {
        logger.error('Error while closing HTTP server.', { error });
        process.exit(1);
      }

      await disconnectDatabase();
      process.exit(0);
    });
  }

  process.on('SIGTERM', () => {
    void shutdown('SIGTERM');
  });

  process.on('SIGINT', () => {
    void shutdown('SIGINT');
  });
}

bootstrap().catch((error: unknown) => {
  logger.error('Application startup failed.', { error });
  process.exit(1);
});
```

Preserve the unhandled rejection and uncaught exception handling
established in IMP-002.

# 24. Add Database Readiness

The existing health endpoint proves the HTTP process is alive. Add a
separate readiness endpoint that verifies required infrastructure.

Create or update:

``` text
src/modules/health/health.routes.ts
```

``` typescript
import { Router } from 'express';

import { checkDatabaseConnection } from '../../config/database.js';
import { successResponse } from '../../shared/responses/api-response.js';

export const healthRouter = Router();

healthRouter.get('/', (_req, res) => {
  res.status(200).json(
    successResponse('Solaís API is healthy.', {
      status: 'ok',
      timestamp: new Date().toISOString(),
    }),
  );
});

healthRouter.get('/ready', async (_req, res, next) => {
  try {
    await checkDatabaseConnection();

    res.status(200).json(
      successResponse('Solaís API is ready.', {
        status: 'ready',
        database: 'connected',
        timestamp: new Date().toISOString(),
      }),
    );
  } catch (error) {
    next(error);
  }
});
```

Endpoints:

``` text
GET /api/v1/health
GET /api/v1/health/ready
```

Operational distinction:

-   Liveness: Is the API process running?
-   Readiness: Can the API serve requests that require the database?

``` typescript
    name: 'Super Administrator',
    description: 'Has full platform administration authority.',
```

# 31. Indexing Rules

Create indexes for actual query patterns.

The initial schema indexes:

-   `users.role_id`
-   `users.status`
-   `users.created_at`
-   `vendor_profiles.application_status`
-   `partner_profiles.application_status`
-   `sessions.user_id`
-   `sessions.expires_at`
-   `sessions.revoked_at`

Do not add speculative indexes to every column. Indexes improve reads
but increase storage and write cost.

-   Event discovery
-   Ticket inventory
-   Order history
-   Payment reconciliation
-   QR check-in
-   Admin filtering

# 32. Referential Integrity Rules

Initial delete behavior:

  -----------------------------------------------------------------------
  Relationship            Behavior                Reason
  ----------------------- ----------------------- -----------------------
  Role → User             `Restrict`              Prevent deletion of a
                                                  role that is assigned

  User → Profiles         `Cascade`               Profile has no meaning
                                                  without its user

  User → Sessions         `Cascade`               Sessions must not
                                                  outlive the user
  -----------------------------------------------------------------------

Future financial records such as orders, payments and issued tickets
must not be casually cascade-deleted. Their retention rules will be
defined in the commerce specifications.

# 33. Data Protection Rules

-   Passwords are hashed before persistence

-   Secrets remain in environment variables

-   PostgreSQL username
-   Password
-   Host
-   Port
-   Database name
-   URL encoding

administrator.

Confirm PostgreSQL is running:

Windows:

``` powershell
Get-Service *postgres*
```

Linux:

``` bash
sudo systemctl status postgresql
```

Run:

``` bash
npx prisma generate
```

## Migration failed

Read the generated SQL and Prisma error before retrying. Do not delete
migration history without understanding the cause.

## Seed creates duplicates

Use `upsert` with stable unique role codes.

# Developer Notes

This document intentionally creates only the database structures needed
for identity, RBAC and session security.

The broader schema should not be implemented all at once. Event,
ticketing, payment, gallery and journal entities will be introduced
alongside their approved feature specifications. This keeps migrations
reviewable and prevents the database from encoding assumptions that the
client has not confirmed.

The database is a long-lived system of record. Schema changes must be
deliberate, migration-driven and documented.
